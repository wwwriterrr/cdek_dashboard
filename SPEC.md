# Alterlit Dashboard — техническое задание

Живой документ. Дополняется по мере появления информации.
Последнее обновление: 2026-09-19.

---

## 1. Назначение

Административная панель для управления предзаказами книг издательства Alterlit.
Основной экран — таблица заказов, с которой ежедневно работают администраторы:
просматривают поступившие предзаказы, меняют их статус и отправляют посылки через СДЭК.

Аудитория: сотрудники со `staff`-статусом. Не публичная страница.

## 2. Технологический стек

| Слой | Решение |
| --- | --- |
| Сборка | Vite 8 |
| UI | React 19 + TypeScript (strict) |
| Состояние | Redux Toolkit |
| Загрузка данных | RTK Query (кэш, инвалидация, polling, задел под сокеты) |
| Стили | CSS с кастомными свойствами, без UI-китов |
| Бэкенд | Django + DRF, `https://alterlit.ru` |

UI-библиотеки (MUI, Ant, shadcn) не используются: таблица плотная и специфичная,
готовые компоненты пришлось бы переопределять целиком.

## 3. Интеграция с Django

Страница отдаётся Django-шаблоном, ассеты подключаются тегами напрямую.

- Статика отдаётся с пути **`/assets/books/dashboard/`**.
- Сборка выдаёт **фиксированные имена без хэшей**: `dashboard.js`, `dashboard.css`.
- Кэш сбрасывается query-параметром версии: `?v={{ DASHBOARD_VERSION }}`.
- Точка монтирования — `<div id="alterlit-dashboard"></div>`.
- `base` сборки настраивается через env `VITE_STATIC_BASE` (по умолчанию
  `/assets/books/dashboard/`), чтобы пути к шрифтам и картинкам внутри CSS
  резолвились от того же префикса.

Шаблон:

```html
<link rel="stylesheet" href="/assets/books/dashboard/dashboard.css?v={{ DASHBOARD_VERSION }}">
<div id="alterlit-dashboard"></div>
<script src="/assets/books/dashboard/dashboard.js?v={{ DASHBOARD_VERSION }}" defer></script>
```

Если `STATIC_URL = "/assets/"`, то же самое через `{% static 'books/dashboard/…' %}`.
Полный пример с командами деплоя — в `django_template_example.html`.

### Разработка

`vite dev` проксирует `/api` на `https://alterlit.ru` (`changeOrigin`, `cookieDomainRewrite`),
чтобы сессионная кука работала с `localhost` без правок CORS на бэке.

## 4. Авторизация

1. При открытии страницы — `GET /api/v1/users/session/self/` с `credentials: "include"`.
2. `200` + `is_staff: true` → доступ есть, рендерим таблицу.
3. `200` + `is_staff: false` → экран «Нет прав администратора», заказы не запрашиваем.
4. `401` / `403` → экран отказа, заказы не запрашиваем.
5. Сессионная кука — `alterlitsessionid`.

```ts
type SessionSelfResponse = {
  id: number | string;
  name?: string;      // отображаемое имя, может отсутствовать
  avatar?: string;    // "/media/avatars/….jpg"
  is_staff: boolean;
  username: string;
  groups: string[];
};
```

Проверено 2026-09-19:

| Запрос | Ответ |
| --- | --- |
| без куки | `403` `{"detail": "Authentication credentials were not provided."}` |
| с валидной сессией | `200` `{"id":1,"name":"Alterlit Developer","avatar":"/media/avatars/….jpg","is_staff":true,"username":"alteruser","groups":[]}` |

В шапке показываем `name`, а если его нет — `username`. Рядом аватар, если он
есть. `groups` пока не используем: под ролевую модель поле уже приходит.

Права признаём только по явному `is_staff: true`. Нет поля, `null`, строка
вместо булева — значит прав нет. Это первый барьер; второй — `403` от бэка
на сами данные.

> Прежняя ручка `users/session/verify/` отдавала только `{"msg": "ok"}`
> и признака прав не давала. Заменена на `self/` 2026-09-19.

### Два вида отказа

`403` приходит в двух разных ситуациях, и сказать администратору надо разное.
Различаем по тексту `detail` от DRF:

| `detail` | Экран | Действия на экране |
| --- | --- | --- |
| `Authentication credentials were not provided.` | «Нужна авторизация» | Войти / Я уже вошёл |
| любой другой (`You do not have permission…`) | «Нет прав администратора» | Сменить учётную запись / Проверить снова |

Разбор терпим к локали: ищем и русские формулировки DRF. Если текст незнаком,
считаем, что пользователь не вошёл — этот экран предлагает вход и выручит того,
кто зашёл не под той учётной записью. На экране «нет прав» ссылка на вход тоже
есть, поэтому ни один из двух случаев не становится тупиком.

Тот же разбор применяется к ошибкам списка заказов: права могут отобрать уже
после проверки сессии, и тогда вместо «повторить» показывается нужный экран.

## 5. Данные

### 5.1 Модели на бэке

`BookPreorder`: `book` → `AlterlitBook`, `user`, `date`, `quantity` (1–20),
`pay_status` (`paid` | `not_paid`), `order_uuid` (СДЭК), `data_json`.

`AlterlitBook`: `title`, `descr`, `slug`, `author_name`, `preorder_price`, `data_json`, …

### 5.2 `GET /api/v1/cdek/orders/`

Контракт **снят с боевого бэка 2026-09-19** (25 заказов в выдаче) и отличается
от первоначального описания: ответ обёрнут в объект, а данные клиента и доставки
приходят плоскими полями рядом с заказом.

Параметры запроса: `?limit=N` — сколько заказов вернуть, по умолчанию `40`.
Список всегда идёт от новых к старым, `limit` обрезает хвост.

```ts
type OrdersResponse = {
  orders: OrderDto[];
  after: boolean;          // true — за пределами limit есть ещё заказы
};

type OrderDto = {
  id: number;
  dt: number;              // int(order.date.strftime("%s")) * 1000 — UTC-миллисекунды
  book: BookDto;
  quantity: number;
  uuid: string | null;     // order_uuid в СДЭК; сейчас null у всех заказов

  name: string;            // ФИО получателя
  phone: string;           // +79135609860
  email: string;
  delivery_point: string;  // код ПВЗ СДЭК, напр. "KSK12"
  delivery_address: string; // полный адрес одной строкой

  pay_status: "paid" | "not_paid";  // добавлено бэком 2026-09-19
  status: OrderStatus;              // добавлено бэком 2026-09-19, коды из 5.4
};

type BookDto = {
  id: number;
  name: string;
  descr: string;
  thumbnail: string;       // путь от корня: "/media/post_images/....png"
  price: number;           // float, напр. 1100.0
  author: string;
  isbn: string;
  author_url: string;
  width: number;           // см
  height: number;          // см
  length: number;          // см
  weight: number;          // г
};
```

Отличия от исходного описания в задаче, учтённые в коде:

- ответ — объект `{orders, after}`, а не голый массив;
- в заказе есть `name` / `phone` / `email` / `delivery_point` / `delivery_address`
  — колонка «Данные клиента» наполняется уже сейчас;
- `uuid` приходит как `null`, не как отсутствующее поле;
- габариты книги — числа, а не строки.

Типы всё равно описаны терпимо (`number | string`, nullable), чтобы фронт не падал,
если сериализатор изменит форму.

Проверено на живом бэке 2026-09-19 (всего 28 заказов):

| Запрос | Вернулось | `after` |
| --- | --- | --- |
| `?limit=3` | 3 | `true` |
| `?limit=26` | 26 | `true` |
| `?limit=40` | 28 | `false` |
| без параметра | 28 | `false` |

### Подгрузка

Курсора бэк не отдаёт — только `limit` и булев `after`. Поэтому «следующая
страница» это тот же запрос с бо́льшим лимитом, а не дозагрузка хвоста:
кнопка «Показать ещё» увеличивает `limit` на 40 и перезапрашивает список.

Чтобы таблица при этом не мигала скелетонами, запрос живёт в одной записи кэша
RTK Query независимо от значения лимита:

```ts
serializeQueryArgs: ({ endpointName }) => endpointName,
merge: (_current, incoming) => incoming,
forceRefetch: ({ currentArg, previousArg }) => currentArg !== previousArg,
```

`merge` просто заменяет данные, потому что ответ всегда содержит список
целиком — с первого заказа, а не продолжение с прошлого места.

Подвал с кнопкой показывается только при `after: true`. При 28 заказах и лимите
по умолчанию 40 его не видно — это правильно.

### 5.3 Расхождение контракта и требований к таблице

| Колонка | Источник | Статус |
| --- | --- | --- |
| Номер заказа | `id` | ✅ |
| Данные клиента | `name`, `phone`, `email`, `delivery_*` | ✅ |
| Дата заказа | `dt` | ✅ |
| Сумма платежа | `book.price × quantity` | ✅ считается на фронте |
| Статус оплаты | `pay_status` | ✅ с 2026-09-19 |
| Статус заказа | `status` | ✅ с 2026-09-19, все 26 заказов в `new` |

**Решение по недостающим полям** себя оправдало: они были описаны в TS-типах как
опциональные, колонки рендерились с плейсхолдером «—». 2026-09-19 бэк добавил
`pay_status` и `status` — обе колонки, чипы-фильтры и цветные полосы статуса
заработали **без единой правки кода на фронте**. Коды статусов совпали
с предложенными в 5.5.

Поля, под которые фронт готов на будущее:

```ts
total?: number;                         // если бэк начнёт считать сумму сам
user?: { id?; name?; email?; phone? };  // если клиента вынесут в объект
```

Сумма: если `total` пришёл — показываем его; иначе `price × quantity`.

### 5.4 Статусы заказа

| Код | Подпись | Смысл |
| --- | --- | --- |
| `new` | Новый | Только поступил, не разобран |
| `in_work` | В работе | Администратор занимается |
| `processed` | Отработан | Данные оформлены, ждёт отправки |
| `reserved` | Бронь | Товар отложен |
| `completed` | Выполнен | Доставлен, закрыт |
| `rejected` | Отказ | Клиент отказался / отменён |
| `lost` | Товар потерян | Проблема, требует вмешательства |

Неизвестный код таблица не роняет — показывает его как есть нейтральным бейджем.

Статусы оплаты: `paid` → «Оплачен», `not_paid` → «Не оплачен».

### 5.5 Предложение по полю статуса на бэке

Коды выше придуманы на фронте. Предлагаемая реализация в Django, чтобы
согласовать её один раз и больше не расходиться.

```python
class BookPreorder(models.Model):
    class Status(models.TextChoices):
        NEW = "new", "Новый"
        IN_WORK = "in_work", "В работе"
        PROCESSED = "processed", "Отработан"
        RESERVED = "reserved", "Бронь"
        COMPLETED = "completed", "Выполнен"
        REJECTED = "rejected", "Отказ"
        LOST = "lost", "Товар потерян"

    status = models.CharField(
        "Статус заказа",
        max_length=20,
        choices=Status.choices,
        default=Status.NEW,
        db_index=True,
        help_text="Внутренний статус обработки заказа. "
                  "Не путать со статусом доставки в СДЭК — тот приходит по order_uuid.",
    )
    # Денормализованный слепок последней смены статуса — чтобы список заказов
    # не ходил в журнал за каждой строкой. Поддерживается только кодом ниже.
    # Важно: НЕ auto_now — иначе метка поедет при любом сохранении заказа.
    status_changed_at = models.DateTimeField("Статус изменён", default=tz.now)
    status_changed_by = models.ForeignKey(
        User,
        verbose_name="Кто изменил статус",
        related_name="+",
        on_delete=models.SET_NULL,
        null=True, blank=True,
    )

    class Meta:
        indexes = [models.Index(fields=["status", "-date"])]

    @classmethod
    def from_db(cls, db, field_names, values):
        instance = super().from_db(db, field_names, values)
        instance._status_in_db = instance.status
        return instance

    def save(self, *args, update_fields=None, **kwargs):
        """Метка времени двигается ровно тогда, когда поменялся сам статус."""
        changed = (
            not self._state.adding
            and self.status != getattr(self, "_status_in_db", self.status)
        )
        if changed:
            self.status_changed_at = tz.now()
            if update_fields is not None:
                # Иначе при save(update_fields=["status"]) метка не доедет до БД.
                update_fields = set(update_fields) | {"status_changed_at"}
        super().save(*args, update_fields=update_fields, **kwargs)
        self._status_in_db = self.status

    def set_status(self, status, *, by=None, comment=""):
        """Единственная точка смены статуса: пишет поле, автора и журнал."""
        if status not in self.Status.values:
            raise ValueError(f"Неизвестный статус: {status}")
        if status == self.status:
            return None

        self.status = status
        self.status_changed_by = by
        with transaction.atomic():
            # status_changed_at проставит save() — см. проверку выше.
            self.save(update_fields=["status", "status_changed_by"])
            return PreorderStatusChange.objects.create(
                preorder=self,
                status=status,
                changed_at=self.status_changed_at,
                changed_by=by,
                comment=comment,
            )
```

**Почему не просто `default=tz.now` и не `auto_now`.** `default` срабатывает
только при вставке строки: метка не «поедет» при сохранении соседних полей,
но и не сдвинется при смене статуса — просто молча протухнет.
`auto_now` даёт ровно обратную беду: время будет обновляться при любом
`save()` заказа, хоть при правке количества. Поэтому инвариант держит `save()`:
сравнивает статус с тем, что был прочитан из БД, и трогает метку только при
реальном расхождении. Автор смены в модели неизвестен — он приходит из запроса,
поэтому его пишет `set_status()`.

Чего этот подход не ловит:

- `BookPreorder.objects.filter(...).update(status=...)` идёт мимо `save()`.
  Массово статус менять не нужно — договоримся не делать этого, а разовые
  миграции данных правят `status_changed_at` явно.
- После `refresh_from_db()` кэш `_status_in_db` на том же объекте остаётся
  старым. В обычном цикле «прочитали → поменяли → сохранили» это не всплывает.

Обоснование остальных решений:

- **`TextChoices`, а не кортеж.** `BookPreorder.Status.IN_WORK` вместо строкового
  литерала в коде вьюх, плюс `get_status_display()` и готовый список для DRF.
  Существующий `PAY_STATUSES` стоит перевести туда же — ради единообразия,
  значения в БД при этом не меняются.
- **`CharField`, а не `IntegerField`.** Код читается в дампе БД, в админке и в
  JSON без словаря соответствий. Фронт уже работает с этими строками.
- **`default="new"`.** Заказ попадает в таблицу сразу разобранным состоянием,
  а не с пустым полем, которое придётся отдельно обрабатывать в интерфейсе.
- **`db_index` и составной индекс `("status", "-date")`.** Таблица фильтруется
  по статусу и всегда сортируется по дате убыванию — это ровно тот запрос.
- **`status_changed_at` / `status_changed_by`.** Когда заказом занимаются
  несколько администраторов, «кто перевёл в отказ и когда» — первый вопрос при
  разборе. Эти два поля — кэш поверх журнала, чтобы список из 25+ строк не делал
  подзапрос на каждую.
- **Переходы между статусами в модели не ограничиваем.** Жёсткий конечный автомат
  на семи состояниях быстро начнёт мешать: реальная работа требует откатов
  («выполнен» → «отказ» при возврате). Достаточно писать, кто и когда менял.

Журнал смен — источник правды, поля на заказе лишь его последняя запись.
Сюда же ложится причина отказа или потери, которой иначе не нашлось бы места:

```python
class PreorderStatusChange(models.Model):
    preorder = models.ForeignKey(BookPreorder, related_name="status_changes", on_delete=models.CASCADE)
    status = models.CharField(max_length=20, choices=BookPreorder.Status.choices)
    changed_at = models.DateTimeField(default=tz.now)
    changed_by = models.ForeignKey(User, null=True, blank=True, on_delete=models.SET_NULL)
    comment = models.TextField("Комментарий", blank=True)

    class Meta:
        verbose_name = "смена статуса предзаказа"
        verbose_name_plural = "смены статуса предзаказов"
        ordering = ["-changed_at"]
```

Если журнал заводить не хочется, `set_status()` всё равно стоит оставить:
он и без записи в журнал даёт одну точку, где статус меняется, — а значит,
одно место, которое надо проверить, когда метка времени разойдётся с фактом.

**Наблюдение по составу статусов.** «Бронь» выбивается из ряда: остальные шесть —
этапы обработки, идущие один за другим, а бронь описывает состояние товара и
может сочетаться с любым этапом (забронированный заказ бывает и оплачен, и в работе).
Если на практике окажется, что бронь снимается и ставится независимо от этапа,
её стоит вынести в отдельное булево поле `is_reserved`, а не держать в том же
перечислении. Пока оставляю в общем списке, как в исходной постановке.

Вью не присваивает `order.status` напрямую, а вызывает
`order.set_status(validated["status"], by=request.user, comment=...)` —
иначе автор смены и журнал останутся пустыми.

### 5.6 `PATCH /api/v1/cdek/orders/<id>/` — смена статусов

Реализовано на бэке 2026-09-19. Меняет `status`, `pay_status` или оба сразу.

```
PATCH /api/v1/cdek/orders/115/   {"status": "in_work"}
PATCH /api/v1/cdek/orders/115/   {"pay_status": "paid"}
PATCH /api/v1/cdek/orders/115/   {"status": "reserved", "pay_status": "not_paid"}
```

Ответ — заказ целиком в том же формате, что и элемент списка.

| Ситуация | Код | Тело |
| --- | --- | --- |
| успех | `200` | объект заказа |
| пустое тело | `200` | объект заказа, ничего не изменилось |
| недопустимое значение | `500` | `{"field":"status","error":"Значение передано неверно"}` |
| заказа нет | `404` | `{"error":"Order does not exist"}` |
| нет прав | `403` | `{"detail": "…"}` |

> **Замечание по бэку.** Недопустимое значение отдаётся с кодом `500`, хотя по
> смыслу это `400`: запрос неверен, а не сервер сломался. Фронт это учитывает —
> распознаёт форму `{field, error}` раньше, чем смотрит на код, иначе показывал
> бы «ошибка на сервере, повторите через минуту». Поправить на `400` при случае.

Формы ошибок у бэка три — `{detail}`, `{error}`, `{field, error}`; разбор в
`describeError` читает все.

#### CSRF

Django требует `X-CSRFToken` на небезопасных методах и на HTTPS дополнительно
сверяет `Referer`. В проде панель на том же домене: токен читается из куки
`csrftoken` через `document.cookie`, `Referer` браузер ставит сам.

В разработке куки `csrftoken` у `localhost` нет, а `Referer` указывал бы на
`localhost` — проверка бы упала. Поэтому прокси Vite подставляет и заголовок,
и `Referer` с `Origin` сам, доставая токен из `VITE_DEV_COOKIE`.

#### Поведение интерфейса

Статус и статус оплаты меняются прямо в таблице — нативным `<select>`,
стилизованным под бейдж. Не своё выпадающее меню: таблица лежит в контейнере
с `overflow-x`, который обрезал бы абсолютно позиционированный список.
Нативный рисуется поверх страницы и бесплатно даёт клавиатуру и мобильные.

Новое значение попадает в таблицу **сразу, до ответа сервера**: администратор
идёт по списку подряд, и ждать круга по сети на каждой строке незачем.
Ответ сервера затем кладётся в кэш целиком — вдруг вместе со статусом
поменялось что-то ещё. Если бэк откажет, правка откатывается, а сверху
появляется плашка с причиной.

Пока PATCH в полёте, оба селекта этой строки заперты — чтобы не отправить
второй запрос поверх первого. Остальные строки остаются рабочими.

Ответ полным объектом заказа, а не `{"ok": true}`: фронт положит его в кэш
RTK Query и обновит строку без перезапроса всего списка.

## 6. Таблица заказов

### Колонки

1. **Номер заказа** — `id` моноширинно. Ниже — UUID СДЭК, если он есть.
   Когда `uuid` пустой, второй строки нет: сейчас он `null` у всех заказов,
   и подпись в каждой строке была бы шумом.
2. **Данные клиента** — имя, телефон, почта. Ниже, за тонкой линией, блок
   доставки: код ПВЗ СДЭК плашкой и полный адрес.
   Линия разделяет «кому звонить» и «куда везти» — при оформлении отправки это
   два разных действия. Колонка тянется по ширине: адрес — самое длинное поле
   таблицы.
   Плашка ПВЗ и адрес открывают **Яндекс Карты в новой вкладке**, см. 6.1.
3. **Книга** — обложка 28×40, название (максимум две строки), автор ссылкой на
   его страницу, ISBN моноширинно, габариты и вес: «33 × 3 × 22 см, 540 г».
   Вынесена в отдельную колонку: в таблице заказов книг это ключевой признак.
4. **Дата заказа** — дата, ниже время. `dt` → локальное время, `ru-RU`.
   Год показывается только у заказов не из текущего года.
5. **Сумма платежа** — итог по правому краю, ниже «цена × количество».
6. **Статус** — бейдж-селект, меняется на месте, см. 5.6. Дублируется цветной
   полосой по левому краю строки, чтобы состояние читалось боковым зрением
   при прокрутке.
7. **Статус оплаты** — селект с точкой, визуально легче основного статуса.
8. **Действия** — пусто. *Состав управляющих кнопок уточняется.*

Раскрытие строки по кнопке «Детали» убрано 2026-09-19: всё его содержимое
переехало в колонки клиента и книги, и раскрывать стало нечего.
Описание книги (`book.descr`) в таблице не показываем — это маркетинговый текст
со страницы книги, администратору он при обработке заказа не нужен.

### Поведение

- Сортировка по дате, сумме, номеру. По умолчанию — новые сверху.
- **Фильтр по статусу** — чипы со счётчиками. Показаны все семь статусов, даже
  с нулевым счётчиком: администратор видит словарь состояний целиком, а не только
  те, что случайно попали в текущую выдачу. Пустые чипы не нажимаются.
  Пока бэк не отдаёт статус, добавляется чип «Без статуса».
- **Фильтр по оплате** — сегментированный переключатель «Любой / Оплачен /
  Не оплачен» со счётчиками. Не чипы: выбор взаимоисключающий, и форма элемента
  должна об этом говорить.
- Фильтры складываются: «В работе» + «Оплачен» сужают выборку вместе.
- Поиск по номеру, UUID, клиенту, телефону, адресу, названию книги и ISBN.
  Запрос из одних цифр ищется и по телефону без форматирования.
- Состояния: загрузка (скелетоны), пустой результат, ошибка запроса с повтором.
- Шапка таблицы липкая, строки не «прыгают» при обновлении данных.

### 6.1 Ссылки на карту

Координат СДЭК не отдаёт, только текстовый адрес и код ПВЗ. Поэтому ссылки
ведут на поиск Яндекс Карт по строке:

| Элемент | Запрос | Смысл |
| --- | --- | --- |
| Адрес доставки | `?text=<адрес>` | здание по адресу |
| Плашка `ПВЗ KSK12` | `?text=СДЭК <адрес>` | сам пункт выдачи |

Обе ведут на `https://yandex.ru/maps/`, открываются в новой вкладке
(`target="_blank" rel="noreferrer"`).

Код ПВЗ в запрос не подставляем: «KSK12» Яндексу ничего не говорит, ищем всегда
по адресу. Слово «СДЭК» в запросе от плашки нужно, чтобы метка встала на пункт
выдачи, а не на здание вообще. Если адреса у заказа нет, плашка остаётся
обычным текстом — ссылку строить не из чего.

Подчёркивание у адреса появляется только при наведении: в таблице из 26 строк
постоянно подчёркнутый адрес превратил бы колонку в частокол.

### Требования к качеству

- Адаптив до мобильного (на узких экранах — горизонтальная прокрутка с закреплённой
  первой колонкой).
- Видимый фокус клавиатуры, навигация по действиям с клавиатуры.
- `prefers-reduced-motion` уважается.
- Контраст текста не ниже WCAG AA.

## 7. Дизайн

Инструмент для ежедневной работы, а не витрина. Плотность важнее воздуха,
скорость считывания важнее эффектности. Единственный выразительный элемент —
ритм строк и цветовая полоса статуса; всё остальное держится тихо.

- **Палитра.** Бумажный нейтральный фон `#F6F6F4`, белые поверхности,
  чернильный текст `#191C21`, волосяные линии `#E4E5E1`.
  Акцент — глубокий печатный синий `#22357A`.
  Семь статусов разведены по тону: отказ нейтрально-серый (штатный исход),
  «товар потерян» красный (авария).
- **Типографика.** `Golos Text` — интерфейс (русская гарнитура Paratype,
  табличные цифры, хороший кириллический рисунок).
  `JetBrains Mono` — только номера заказов и UUID, где важно посимвольное сравнение.
- **Строки** двухуровневые: главное значение и приглушённое уточнение под ним.
  Это держит плотность без потери читаемости.
